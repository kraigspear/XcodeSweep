# XcodeStorage: seams only at the OS edges, and different cancellation for scan and delete

`XcodeStorage` is one deep module. Its only substitution points are the four things that touch the OS: the Xcode root folder, `CommandRunning` (`xcrun simctl`), `FileTrashing`, and the `now` clock. Scanning, classification, sizing, and deletion sequencing are concrete internal code with no protocols. We rejected a service layer behind a protocol, with a live and a mock implementation (the glossary's avoided `StorageService` / `LiveStorageService` / `StorageManager` names). Because the seams sit at the OS edges, tests run the real classification and sequencing against a temp folder (`TempXcodeFixture`) with a stubbed runner and trasher. A mocked service would replace exactly the logic most worth testing. Add a new seam only for a new OS dependency, never to mock part of the module.

`scan()` and `delete(_:)` deliberately handle cancellation differently, because the store needs different things from each:

- **Scan awaits teardown before it throws.** A scan runs category scans and `simctl` children concurrently. When a scan is cancelled, `XcodeSweepStore` restores the previous inventory, and it never lets a scan and a deletion overlap (#5 removed `itemIDsDeletedDuringScan` for this reason). If scan work kept running after the caller saw `CancellationError`, it could overlap the next operation. So when cancellation is observed in `next()`, the iterator throws only after the producer task and its child tasks have exited. The store returns from its loop as soon as `.completed` arrives, without the final pull; that is safe because every category scan has finished before `.completed` is emitted. Abandoning a scan before `.completed` only requests cancellation and does not wait; the store never does that.
- **Delete is pull-based and reports each acknowledged removal.** Deleting one item per `next()` means no work exists that the caller has not asked for, so there is nothing to tear down. The store removes each `.deleted` item from the inventory as it arrives and keeps those acknowledged removals after a cancel. A Trash move cannot be interrupted once it starts. If one finishes, its outcome is emitted before cancellation is thrown. A cancelled `simctl` deletion is different: the command may have taken effect before its result reached Swift, so that item's outcome is unknown until the next scan. Cancellation is never recorded as a `DeletionFailure`, because it is an interruption, not a failure.

This would change if deletion became concurrent. It would then need a producer and the same awaited teardown that scan uses.
