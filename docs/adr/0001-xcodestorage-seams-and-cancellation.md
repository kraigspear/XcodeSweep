# XcodeStorage: seams only at the OS edges, and different cancellation for scan and delete

`XcodeStorage` is one deep module. Its only substitution points are the four things that touch the OS: the Xcode storage locations (`XcodeLocations`: the Xcode folder, plus DerivedData and Archives, which Xcode's Locations settings can move), `CommandRunning` (`xcrun simctl`), `FileTrashing`, and the `now` clock. Scanning, classification, sizing, and deletion sequencing are concrete internal code with no protocols. We rejected a service layer behind a protocol, with a live and a mock implementation (the glossary's avoided `StorageService` / `LiveStorageService` / `StorageManager` names). Because the seams sit at the OS edges, tests run the real classification and sequencing against a temp folder (`TempXcodeFixture`) with a stubbed runner and trasher. A mocked service would replace exactly the logic most worth testing. Add a new seam only for a new OS dependency, never to mock part of the module.

Cancellation is user-triggered. `XcodeSweepStore` owns the running operation's task, so Stop (scan) and Cancel (deletion) cancel it directly; the initial scan is also cancelled when the view that started it goes away. Either way the store stays busy until teardown finishes, so a Stop followed at once by Refresh or Delete cannot overlap the operation being stopped.

`scan()` and `delete(_:)` deliberately handle cancellation differently, because the store needs different things from each:

- **Scan awaits teardown before it throws.** A scan runs category scans and `simctl` children concurrently. When a scan is cancelled, `XcodeSweepStore` restores the previous inventory, and it never lets a scan and a deletion overlap (#5 removed `itemIDsDeletedDuringScan` for this reason). If scan work kept running after the caller saw `CancellationError`, it could overlap the next operation. So when cancellation is observed in `next()`, the iterator throws only after the producer task and its child tasks have exited. The store returns from its loop as soon as `.completed` arrives, without the final pull; that is safe because every category scan has finished before `.completed` is emitted. Abandoning a scan before `.completed` only requests cancellation and does not wait; the store never does that.
- **Delete is pull-based and reports each acknowledged removal.** Deleting one item per `next()` means no work exists that the caller has not asked for, so there is nothing to tear down. The store removes each `.deleted` item from the inventory as it arrives and keeps those acknowledged removals after a cancel. A Trash move cannot be interrupted once it starts. If one finishes, its outcome is emitted before cancellation is thrown. A cancelled `simctl` deletion is different: the request may already have reached CoreSimulator, so that item's outcome is unknown until the next scan. That scan starts at once: however a deletion ends, the store rescans in the same operation, and a completed rescan also refreshes free space and marks devices of a deleted runtime unavailable. Stopping that rescan restores the inventory from when it began, which already omits the acknowledged removals, so only those reconciliations are skipped. A cancelled run still reports what it removed and what failed before the stop. Cancellation is never recorded as a `DeletionFailure`, because it is an interruption, not a failure.

A stopped command never outlives the call that ran it. On cancellation or timeout `ProcessRunner` sends SIGTERM and throws only after the child has exited, sending SIGKILL after a short grace period. So a scan or deletion that has finished stopping has no `simctl` process left running to overlap the next operation. It does not wait for descendants that hold its pipes; those can't touch simulator state through it.

`simctl` list commands run with a per-call timeout (`XcodeStorage.simctlListTimeout`); destructive commands (`shutdown`, `delete`, `runtime delete`) run without one. A hung list only delays a read, so aborting it costs nothing: the category records a scan failure, which it shows, and the next scan retries. A slow delete may still be taking effect, so a timeout would leave the same unknown outcome as a cancel while making it happen without the user asking; stopping a deletion stays the user's decision.

This would change if deletion became concurrent. It would then need a producer and the same awaited teardown that scan uses.
